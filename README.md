# Grunions Water Polo team app
Flask + SQLite. Dark, mobile-first. Runs locally or on Render/any Docker host (see Deploy).

## Run
    ./run.sh    # reads .env.local (BOT_API_KEY, SECRET_KEY, ADMIN_EMAIL, optional VERIFY_WEBHOOK_URL); port 5055
or:
    python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
    ADMIN_EMAIL=you@yourmail.com SECRET_KEY=$(openssl rand -hex 32) .venv/bin/python app.py   # http://localhost:5055
Env: PUBLIC_URL (base URL for QR + login links), EXPIRING_DAYS (default 30), CRON_KEY (lets a scheduler call /api/expiring?key=...),
DEV_SHOW_LINKS=1 (local testing only: show magic link on screen; default 0), SECURE_COOKIES=1 (behind HTTPS), GRUNIONS_DB, PORT.
Demo data: `rm grunions.db && .venv/bin/python seed_demo.py` (admin eli@example.com, coach marcus@example.com).
Tests: `.venv/bin/python test_app.py` (304 checks) and `.venv/bin/python -m pytest -q test_v2.py` (16 tests), `.venv/bin/python -m pytest -q test_google.py` (10 tests). Run each in its own process, or just `./run_tests.sh`. Daily job: `.venv/bin/python daily_expiry.py [--days 30] [--remind]`.

## Roles
member (athlete), active coach (check-in + #coaches), admin (People and the rest of admin). Manage on Admin → **People** (/members), with segments Members, Coaches, Admins, and Referees. The Roles tab is gone. Only admins can open People. The last admin can't remove themselves.
Make admin and Make coach work for any member, whether or not USA Water Polo has verified them. Remove admin and Remove coach take that access away. On Members, a colored dot for the USAWP status (green, amber, red, or gray) sits in front of the name, and the ⋯ menu is at the far right of the row. Tap the row to open the same detail panel as check-in. The panel is read-only: a status line (Cleared, Expiring soon in N days, Expired, or Not verified) with one reason, then USAWP # with a dot and the expiry, then SafeSport, background screening, and referee, each with a dot and a date like Nov 3, 2026 or Not on file. A Coach chip sits on that status line when the person is a coach, on the coaching list, or coach-eligible. Dates in this panel are written out, not ISO. Who verified them is a muted footer. The bot note is behind Details. Recheck, Edit, and Ask Grunions are pills under the summary. Edit and Recheck open one sheet titled with Edit and the member's name, with membership, clearances, and preferred name, and one Save. Empty dates say Not on file · add date. Recheck scrolls that sheet to Membership. Ask Grunions sends the bot request and shows a toast. Saving still records the admin and the Pacific time, recomputes Coach eligible and Referee eligible, adds a Coach membership to the coaching list without granting coach access, and answers a pending verification request. Background screening is required only for an active coach. An admin who is not an active coach does not need it, and a player never does. On Members, the ⋯ menu offers Make admin or Remove admin, Add to coaches or Remove from coaches, and Add to referees or Remove from referees. Each change shows a short confirmation. The last admin cannot remove their own admin role. Coach access (check-in and coaches chat) comes only from Make active coach. The coaching list is who can be assigned to a practice. Make active coach does not add someone to that list, and being on the list does not open check-in or coaches chat. Admins are not on that list unless someone adds them. A verified USAWP membership type with the word coach (for example Individual Membership, Coach) adds that person to the coaching list automatically. Edit practice offers a Coaches checkbox for each person on that list. People shows Active coach, Coach for the coaching list, and Coach eligible. Coach eligible is a verified coach membership with current background screening and SafeSport.
Coach eligible is separate from those roles. It shows when a USAWP coach membership is verified and both background screening and SafeSport are current, including on the expiry date itself. The badge is on the home card when there is no Coaching row, the practice coach picker, the practice page, the members CSV, and the Practices and Practice Coaches sheet tabs. The check-in list does not show a Coach eligible badge or a background screening line on the collapsed row. The expanded row shows the Coach chip instead. An active coach's expanded home card shows the Coaching row and does not repeat Coach eligible under it. On every People tab, a coach row uses one chip, Coach · expires and the earliest of the background screening, USAWP membership, and SafeSport dates. The chip is grey when that date is current, yellow when it is inside the expiring window, and red when it is expired or the coach is not eligible. An admin has an Admin chip on every People tab. The background screening line stays in the expanded details, not on the collapsed row. If one of those dates has passed, the line is Coach eligibility expired and that date. A practice with no coach-eligible assigned coach shows that warning to admins on the practice page, and on check-in. Referee eligible uses the same dates for a membership type with the word referee, filled in when a verification result includes that membership and its expiry. The badge is on People (the Referees segment, including a Referee eligible section for people not on the referee list yet), on check-in, and in the Referee eligible column of the members CSV and Members sheet. Add to referees puts someone on that list. A past date reads Referee eligibility expired and that date, and the filter hides that person.
ADMIN_EMAIL (comma-separated) bootstraps admins and keeps them admin on every start; remove an address there to demote it.

## Verification bot API
- Home form or admin "Ask Grunions to verify" creates a verify_requests row (pending). The Home form, if one is already pending, updates that row's member_number instead of inserting another. Admin "Ask Grunions to verify" does not create a duplicate while one is pending.
- Whenever a verify request is created, if VERIFY_WEBHOOK_URL is set, POSTs this JSON (5 s timeout). Failures are logged only and never break the page. A member submitting their own number from Home still sends it.
  `{"request_id": 12, "member_id": 4, "name": "Ana Lopez", "preferred_first": "Ana", "email": "ana@example.com", "member_number": "5555555", "requested_by": "Eli Joern", "member_submitted": false, "app_url": "https://grunions.example"}`
  `requested_by` is the name of the person who asked (the admin, or the member when they submit it themselves). `member_submitted` is true only when that member submitted the request. `app_url` is PUBLIC_URL. `member_number` and `requested_by` are stored on the request. If VERIFY_WEBHOOK_KEY is set, the POST sends `Authorization: Bearer <key>`. If VERIFY_WEBHOOK_HEADER is set, that name is used instead and the value is the raw key (no Bearer prefix).
- Auth: `Authorization: Bearer $BOT_API_KEY` (401 otherwise; API disabled if unset).
- GET /api/verify-requests?status=pending|done → list.
- POST /api/verify-requests/<id>/result  {"verified":true,"member_number":"123","membership_expires_on":"2027-08-31",
  "membership_type":"Individual Membership, Coach","compliance":{"SafeSport training":"2027-05-01"},"note":"..."} → updates member + compliance (matched by requirement name or keyword),
  marks done (409 if already answered) and posts an in-app notice to every admin. It does not post to chat. The member's card updates, and they get the verification-result push when that notification is on.
  When verified is true and membership_type contains the word coach, the member is added to the coaching list. That does not grant coach access. A verified result whose membership type is not a coach membership removes only a USAWP-sourced list row. A failed result, or a result with no membership_type, leaves the list unchanged. Mark membership verified does not set a membership type and does not change the list.

## Deploy (Render)
`render.yaml` defines a Docker web service (gunicorn, 1 worker x 8 threads since SQLite) with a 1 GB persistent disk at `/data` (`DATA_DIR=/data`).
New → Blueprint → point at the repo, then fill PUBLIC_URL and the SMTP_* values. Other hosts: `docker build -t grunions . && docker run -p 10000:10000 -v grunions-data:/data --env-file prod.env grunions`.
Without Docker: `gunicorn app:app --bind 0.0.0.0:$PORT --workers 1 --threads 8`.

## Sport:80 roster import columns
Transfer import takes .csv or .xlsx (title rows above the header are skipped; headers matched case/space/punctuation-insensitively):
- **First Name / Last Name** (or Name / Full Name), **Email / Email Address** — matching (email first, then unique legal first+last). Optional **Preferred First Name / Nickname** is stored as the name shown in the app and is not used to match.
- **ID Number / Member Number / Membership Number** — stored as USAWP #. **Contact ID** — stored as sport80_contact_id.
- **Status / Membership Status** and **Valid Until / Expiry Date / Membership Expiry Date** — status. If there's no status column, a future expiry counts as current.
- **Membership Type / Member Type** — stored on the member. A value with the word coach (not coaches or coaching) adds them to the coaching list. Any other value removes only a USAWP-sourced list row.
- Any column containing a requirement keyword (safesport, background; editable in Rules) plus expiry/valid through/completed/status updates that item. Club waiver and concussion columns are ignored.
A file needs a name or email column plus at least one of status, member number, or expiry.

## Sign in with Google
OpenID Connect via Authlib (state + nonce, ID token checked). Requires `email_verified`. Signs in only when that Google email matches an existing member who registered at /join (case-insensitive). It does not create an account. If there is no registration, the login page says so and offers a Sign up button to /join. An existing admin with that email still signs in, including one created outside /join. Admin is never granted by Google sign-in, only via ADMIN_EMAIL or People.
Redirect URI: `PUBLIC_URL + /auth/google/callback`, e.g. `https://grunions-team-app.onrender.com/auth/google/callback`
(locally without PUBLIC_URL: `http://localhost:5055/auth/google/callback`).

Google Cloud Console setup:
1. https://console.cloud.google.com → project picker → **New project** (e.g. "Grunions") → select it.
2. **APIs & Services → OAuth consent screen** (Google Auth Platform → Branding/Audience): User type **External** → app name "Grunions Water Polo", support email, developer contact email → Save.
   Scopes: add `openid`, `.../auth/userinfo.email`, `.../auth/userinfo.profile` (non-sensitive, no verification review needed).
3. **Audience → Publish app** (move from Testing to **In production**) so any Google account can sign in. In Testing, only listed test users can.
